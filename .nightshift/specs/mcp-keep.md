# McpKeep executive spec

## Outcome

Build McpKeep, a small Python MCP server using gkeepapi, for one configured Google account. Hermes runs on Windows on the same machine and launches the server over stdio. Include a working Hermes configuration example. HTTP hosting is outside this scope.

## Tool surface

Expose exactly these four tools, with machine-readable results and stable Google Keep note IDs:

| Tool | Behavior |
| --- | --- |
| `list_notes` | List active, archived, or all notes, with bounded pages and optional text filtering. Default to active notes. Return IDs and useful summaries for selecting a note, including creation and last-edit times. |
| `read_note` | Read a note by ID, including its text, checklist items, labels, archive status, creation and last-edit times, attachment counts, and web links. Preserve checklist order, checked state, and nesting in the returned representation. |
| `archive_note` | Archive one note by ID. Already archived is a successful no-op. |
| `unarchive_note` | Restore one archived note by ID. Already active is a successful no-op. |

Trashed and deleted notes are excluded from every operation. Unknown, trashed, deleted, and non-note IDs produce clear errors. Empty listings succeed with an empty page. Invalid filter and pagination arguments fail without performing a mutation. Pagination must communicate whether more results exist; documentation states how changes between calls affect traversal.

No creation, content editing, deletion, checklist changes, or bulk mutations. Archive and unarchive preserve titles, bodies, labels, checklist contents, and other unrelated note data. Image, drawing, and audio download is outside this scope; reading their containing notes still returns available textual content, together with how many of each the note holds, so a caller can tell when the text alone is incomplete. Times come from Google's own note metadata, never from timestamps the SDK generates locally.

## Connection and authentication

Use stdio MCP with all diagnostics on stderr. Hermes owns subprocess startup and shutdown. Tool discovery must work before Google credentials are configured, so setup failures appear on tool calls instead of hiding the server's tool surface.

Use the agreed unofficial gkeepapi backend. Its Google master token has broad account access; the four-operation restriction is enforced by this server. Store the token outside the repository and configure its file path rather than putting the secret in Hermes configuration. Provide a separate local authentication setup command. Secrets must stay out of tool results and logs, including failure paths. Do not accept the Google account password as a tool argument.

One account is configured per server process. Document credential changes and recovery so restarting the server picks up replacement credentials. The server must not persist note data or pending mutations to disk; the importer's vault copies are its deliberate output, not a cache. A failed mutation must not remain queued and be sent by a later read or unrelated operation.

## Failure and recovery

Return clear MCP tool errors for missing or unreadable credentials, unavailable notes, authentication failures, and Google failures. Read current server data before deciding what to archive or unarchive. Serialize overlapping operations against shared client state.

Report success only after the archive change has synchronized successfully, or after observing the requested state for a no-op. If a write may have reached Google but confirmation failed, report the uncertain outcome and direct the caller to read the note before deciding whether to retry. Never turn an uncertain outcome into a success or automatically replay a failed write. Later reads must rebuild trustworthy state rather than upload pending mutations.

Protect reads and writes from consequential hangs and unbounded retry behavior. Local credential or argument errors should be actionable without disclosing secrets. Preserve user note content across all normal and failure paths.

## Obsidian importer

`mcp_keep.importer` is a command-line companion, not an MCP tool. It copies notes from Keep into an Obsidian vault inbox and then archives them, so Keep empties as the vault fills. It reuses the server's worker, credentials, and archive guarantees, and involves no model, so note text arrives unchanged.

- Selection: active notes only, oldest creation time first, a bounded number per run. Pinned notes and notes carrying a configurable skip label stay in Keep.
- Order per note: write the file, verify it by reading it back, record the Keep ID as `imported` in a ledger inside the vault, then reread the note and verify its current rendering against the file. The importer sends the SHA-256 fingerprint of the complete read-note representation serialized as ASCII JSON with sorted keys and compact separators. The worker compares it with the fingerprint of its own fresh snapshot before authorizing a mutation. This internal `expected_fingerprint` field is exactly 64 lowercase hexadecimal characters; invalid values fail before authentication. Ordinary MCP archive calls omit it and retain their existing behavior. Already-archived notes are successful no-ops regardless of fingerprint. A note is never archived before its copy is verified and recorded.
- Ledger: vault-local, append-only JSON lines contain string `keep_id`, `path` relative to the vault, `status`, and `at` (the original local import time as ISO 8601 with seconds and offset). State is `imported` while archive confirmation is pending, `held_pending_report` for media awaiting warning delivery, `held` after delivery, or `completed` after archive confirmation. A pending report also contains string `report`, the warning with title whitespace collapsed to spaces and the original relative path; other states need no report field. A missing ledger starts empty; repeated IDs use the last complete entry. An incomplete final line is dropped; an unreadable complete line, including a pending report without string report text, stops the run. Old `imported` entries follow the pending lifecycle; old `held` entries count as already reported because the historical ledger retained no delivery evidence. Paths outside the vault are rejected before a copy is used.
- Recovery before the ledger write: identify the Keep ID only inside closed frontmatter of an inbox Markdown file. Stream through the closing delimiter, retaining only identity and import-time fields and enough repeated values to reject duplicate provenance. Both fields use root-level plain keys and accept one-line plain, single-quoted, or double-quoted scalar text with optional trailing YAML comments. Compose values in mapping-value context with pinned PyYAML's BaseLoader to preserve timestamp and document-marker-shaped text; accept only string-tagged ScalarNodes in those styles. Track the current provenance key while streaming; a new root field clears it, while blank or comment lines retain it. Indented content following either provenance field is unsupported even across blank lines or comments. If no keep_id is present, ignore the file's metadata. Otherwise, collections, block scalars, indented continuations, non-string tags, multiple documents, malformed YAML, and parser recursion failures are unreadable provenance and stop the run. Reuse one matching copy without rewriting, after verifying it against the current note using the copy's original import time. Duplicate matches, incomplete or duplicate provenance, or changed copies stop the run and leave Keep untouched. Manually archiving the Keep note clears its pending archive obligation but does not make unreadable frontmatter usable; it must still be repaired or the file moved outside the inbox before new imports can scan past it.
- Recovery after the ledger write: process pending IDs before new imports, with both counting toward the run limit. Reread each pending note; if already archived, append `completed` without a mutation, including when its local copy is absent. Otherwise, require the current copy to match before a conditional archive attempt. Missing, unreadable, changed, or unavailable state stops the run for manual reconciliation; new media must not be archived. Messages may report a specific copy, a shared Keep ID, or a validation constraint; transient read failures may use generic Keep errors. A note gone from Keep (trashed, deleted, or unknown) is told apart from other read failures through the worker's shared unavailable-note message; its obligation is discharged only by restoring the note or by the user appending an explicit `completed` ledger line. Pinned or skip-labelled pending notes stay pending and do not block other eligible notes. Failure retains the pending obligation. A crash after archive confirmation but before the completion append resumes by observing the archived state; a partial completion append is dropped, leaving the earlier pending entry in force.
- Completion: `held_pending_report`, `held`, and `completed` IDs are never read individually or mutated again, even if restored or edited in Keep or their vault copy is moved or removed. Pending warnings are delivered from ledger text alone. To deliberately reimport after manual reconciliation, move the prior copy outside the inbox and remove all ledger lines for that ID. No implicit invalidation clears a pending obligation.
- Media reporting: a note with attachments is imported with a visible warning and left in Keep. Persist `held_pending_report` with the warning before printing it, then print and flush before appending `held`. Later note failures do not suppress earlier warnings. A crash before the initial ledger write resumes through the unrecorded-copy path; a partial pending line is dropped and resumes the same way. A complete pending line with no output retries delivery on the next run, before contacting Keep. A crash or failed acknowledgement after output may repeat the warning, giving at-least-once delivery. A partial acknowledgement is dropped, retaining the prior pending warning. A complete `held` entry prevents repeat reports. Delivery never rereads or rewrites the note, and dry runs preview warnings without acknowledging them.
- Output: empty on success, one line per held note, and a failure message with a nonzero exit. An OS lock refuses overlapping runs. A dry run leaves Keep, vault notes, and the ledger unchanged, though acquiring the lock can create its directory and file.

Offline tests cover each rule above, plus a run end to end through the real worker against the offline fixture.

## Acceptance evidence

Offline tests exercise the actual MCP protocol and gkeepapi data structures without contacting Google. Verify exactly four advertised tools, active/archive/all filtering, text filtering, bounded pagination, empty results, invalid arguments, checklist reads, server-sourced times, attachment counts, unavailable-note errors, idempotent archive/unarchive, archive round trips, preservation of unrelated data, overlapping calls, and recovery after authentication, read, and write failures. Verify that sensitive backend error text cannot escape through MCP responses or stderr.

Include dependency locking, local authentication instructions, Windows setup commands, and the Hermes stdio configuration. Use the supported Python SDK surface verified against the installed package. Run scoped tests and relevant static checks, and distinguish offline evidence from live Google verification. If credentials are unavailable, deliver the tested server and setup instructions while explicitly reporting that live Google verification remains unperformed.

Deliver locally under the repository's Git conventions. Publication and deployment require separate user direction.
