## Entries

- **Add a correlation ID to the consultation lifecycle log lines** (shipped 2026-11-12). The `Consult` tool method in `McpConsultant/Tools/Consultant.cs` now mints an eight-hex-character ID from a new GUID at the start of each call and writes it in brackets into every lifecycle line: `Consultation started`, both `Consultation completed` forms, `Consultation cancelled`, and the error line, now `Consultation failed [id]: <error>`. The ID lives in the message text rather than a logger scope: the simple console formatter prints scopes only with `IncludeScopes` enabled and then on a separate line, and the live cancellation test's harness matches one physical stderr line at a time. (The formatter writes each entry as a timestamped header line followed by the message line, so the README's registration-time check finds a call's message lines by ID and reads each timestamp from the header line above.) With exact pairing available, the single-in-flight precondition was dropped from `README_CONSULTANT.md` and from the cancellation probe and registration-time check in `.nightshift/features/mcp-consultant.md`, which also records the ID design. Unit tests in `ConsultantToolTests` capture the log lines and assert shared and distinct IDs across the success, cancellation and failure paths; the live cancellation test now asserts the cancelled line carries its started line's ID, but like the rest of the live suite it was compiled, not run, since it makes paid OpenRouter calls.
- **Log validation errors as `Consultation failed` lines** (shipped 2026-11-12). The `Consult` tool method in `McpConsultant/Tools/Consultant.cs` used to return the errors its own validation detects before any request (empty question, invalid effort, missing default model, non-positive `TimeoutSeconds` or `MaxAttachmentBytes`, missing API key, file validation failures) without logging, so a rejected call left no trace on stderr; only exception-mapped errors went through `LogAndReturn`. Every validation return now goes through `LogAndReturn` too, so each structured error logs one `Consultation failed [id]: <error>` line, with no preceding `Consultation started` line since the request was never sent. Two `ConsultantToolTests` cases cover it, one for an empty question and one for a missing file, since file validation hands back its error through the validator's result rather than a direct error-message call. The Error handling summary in `.nightshift/features/mcp-consultant.md` again states that every structured error is logged.
- **Reword or strengthen the smoke-call threshold in `README_CONSULTANT.md`** (shipped 2026-11-12). Part two of the registration-time check, a heavy consultation through the registered client that must run past 100 seconds, was presented as establishing "the long-running path", although a call over 100 seconds proves only that the client tolerated that call, not that it waits the full `TimeoutSeconds` (300 by default). The rewording option was taken: `README_CONSULTANT.md` and the registration-time paragraph under Testing in `.nightshift/features/mcp-consultant.md` now both say a pass shows only that no effective ceiling cut off a call that ran that long, not that the client waits the full `TimeoutSeconds`, which rests on part one's inspection of `MCP_TOOL_TIMEOUT`. Both name an unadvertised limit as an example of such a ceiling; the README additionally calls a pass a spot check and adds a shorter built-in default as a second example. The 100-second floor, the re-run-when-inconclusive rule and part one are unchanged, and nothing is claimed about the value of Claude Code's built-in default. The alternative, extending the procedure to drive a call near the configured ceiling, was not taken: it needs a paid `effort: max` call that is hard to pin to a runtime, and one that overshoots fails against the server's own timeout.
